# Paper Reproduction: PWL Core and Section IV Simulations

[中文](README.zh-CN.md) | English

This directory implements the PWL mathematical structure and the BCD–ADMM optimization method from the paper *Physics-Informed Weakly-Supervised Learning for Quality Prediction of Manufacturing Processes*, providing a runnable, auditable research baseline. It is an independent implementation — **it is not the original authors' official code, nor does it claim to strictly reproduce every table value**.

[Repository home](../README.md) · [Technical implementation and assumptions](REPRODUCTION.md) · [Heat-conduction transfer](../migration/README.md) · [Current project status](../docs/CURRENT_STATUS.md)

## What is implemented

| Module | Content |
|---|---|
| `src/pwl_repro/core/` | FeatureSpec, PWLRegressor, BCD–ADMM, sparse proximal operators |
| `src/pwl_repro/scenarios/` | Simulation data and feature libraries per paper equations (9)–(11) |
| `src/pwl_repro/experiments/` | Tuning, nested splits, experiment protocols, statistics, and result output |
| `configs/` | Smoke, everyday-scale, paper-scale, and sensitivity configurations |
| `tests/`, `scripts/` | Regression tests and independent numerical verification |
| `reports/` | Reproduction audits and discrepancy explanations; `legacy/` holds historical analyses |

The model structure is `y_hat = H(x_ph, theta) g + B(x_pr, x_ph) d`. Scenario-agnostic algorithms live in `core`; each scenario must provide its physics model and suitable basis functions — one scenario's H/B library cannot be applied wholesale to all tasks.

## Environment setup

If you have not cloned the repository yet, follow the [home-page setup steps](../README.md) using the `HeatTest` branch. The two application packages share the root-level environment; **run all commands below from the repository root**.

```sh
uv sync --locked --python 3.11 --extra dev
uv run python reproduction/run_reproduction.py --help
```

uv must be installed beforehand; the project's Python range is ≥3.11, <3.14, and this verification used 3.11. Simulation data is generated by in-repo code — no external experimental data or commercial simulation software is needed.

## Minimal run

First check the end-to-end flow with a small configuration:

```sh
uv run python reproduction/run_reproduction.py --config reproduction/configs/smoke.yaml --mode sample-size --output reproduction/results/quickstart
```

The output directory is created by the program. Reusing the same directory may overwrite artifacts; specify a new directory for each formal run. Smoke verifies the program flow, not agreement with the paper's numbers.

## Choosing an experiment protocol

| Goal | Configuration and parameters |
|---|---|
| Quick check | `configs/smoke.yaml` |
| Everyday simulation | `configs/default.yaml` |
| Trend diagnosis | `configs/diagnostic.yaml` |
| Paper scale | `configs/paper_protocol.yaml`; the full grid is significantly more expensive |

The simulation `--mode` supports `sample-size`, `physics-accuracy`, `label-savings`, and `all`. The default mode is `sample-size`; it does not automatically run all protocols.

```sh
uv run python reproduction/run_reproduction.py --config reproduction/configs/default.yaml --mode all --output reproduction/results/default_recheck
```

Split rules, correlation targets, and statistical criteria are in the [Section IV protocol](SECTION_IV_PROTOCOL.md). Selection rules and stabilization terms come from the specific configuration; do not mistake the simulation's 1-SE rule for the default of all transfer scenarios.

## Data sources and reproduction boundary

- **Simulation data**: generated by the in-repo generator per configuration and seed. H/B, input covariance, singular-point rejection sampling, and noise criteria contain engineering assumptions — see the [technical notes](REPRODUCTION.md).
- **Scope limit**: this directory provides only the Section IV numerical simulations; other experimental cases from the original paper are not implemented by, nor results of, this project.
- **Parameter interpretation**: whether calibration parameters are physically identifiable depends on the specific scenario; predictive accuracy alone cannot prove correct parameter recovery.

## Output and verification

Output includes `results.csv`, predictions, condition and configuration records, summaries, figures, and `quality_checks.csv`; the exact file set varies with scenario/mode. Run artifacts are Git-ignored by default; a fresh clone has no historical training results. Local figure references in reports may require running the corresponding configuration first.

```sh
uv run pytest reproduction/tests
uv run python reproduction/scripts/verify_sim_correctness.py
```

Verification records for the currently retained scope are in [current status](../docs/CURRENT_STATUS.md). Passing tests does not mean the paper's numbers match exactly or that all scientific quality anchors hold.

## Troubleshooting and contributing

- Data or config not found: first confirm the current directory is the repository root.
- Missing dependencies: use the root-level `uv sync --locked --python 3.11 --extra dev`; do not create subdirectory environments.
- Full grid too slow: run smoke first; parallelism scale is config-controlled.
- GP boundary warnings or quality-check failures: judge together with the configuration and `quality_checks.csv`; a process ending normally does not mean the experiment's assumptions hold.

When filing an issue, attach the run command, configuration, Python version, and a log excerpt; when modifying the core, run the related tests and independent numerical checks. When citing results, record the original paper, data sources, repository commit, and configuration, and state the engineering assumptions explicitly.
